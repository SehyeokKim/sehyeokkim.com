# 0001. 브랜치 전략: GitHub Flow + Squash merge

- 상태: 채택
- 날짜: 2026-10-15

## 배경

- 개발자 1명이 운영하는 저장소이고, `main`에 병합되면 GitHub Actions가 바로 운영 환경에 배포합니다.
- 릴리스 버전이나 정해진 배포 주기가 없습니다. 변경이 준비되면 그때그때 배포합니다.
- 변경 이력을 리뷰 단위로 읽을 수 있어야 합니다. 저장소 히스토리 자체가 "어떻게 만들었는가"를 보여 주는 자료이기 때문입니다.

## 결정

**GitHub Flow**를 따르고, 병합은 **Squash merge만 허용**합니다.

- `main`은 항상 배포 가능한 상태를 유지하고, 운영 환경과 같습니다.
- 모든 변경은 `main`에서 딴 짧은 작업 브랜치에서 하고, PR로만 `main`에 들어갑니다.
- 브랜치 이름은 커밋 접두어와 맞춥니다: `feat/`, `fix/`, `infra/`, `ci/`, `docs/`, `chore/`
- PR 제목이 그대로 `main`의 커밋 메시지가 됩니다. 그래서 PR 제목은 `접두어: 한국어 요약` 형식으로 씁니다.
- 병합된 브랜치는 자동으로 삭제합니다.

`main` 보호 규칙으로 이 흐름을 강제합니다.

| 규칙 | 목적 |
|---|---|
| PR 필수 (승인 0명) | 직접 push 금지. 1인 저장소라 승인 수는 0으로 둠 |
| 관리자도 우회 불가 | 저장소 소유자도 같은 규칙을 따름 |
| Linear history | 병합 커밋 없이 일직선 히스토리 유지 |
| 대화 해결 필수 | 남긴 리뷰 코멘트를 처리한 뒤에만 병합 |
| Force push · 브랜치 삭제 금지 | 공개된 히스토리를 고쳐 쓰지 않음 |
| 필수 상태 검사 | CI 통과 전 병합 금지 (CI 추가 후 적용) |

## 대안

| 대안 | 채택하지 않은 이유 |
|---|---|
| **Git Flow** (`main` · `develop` · `release` · `hotfix`) | 정해진 주기로 버전을 내는 제품과 여러 명이 일하는 팀에 맞는 방식입니다. 이 저장소는 병합이 곧 배포라서 `develop`을 거치면 같은 변경을 두 번 병합하게 되고, 히스토리만 늘어납니다. |
| **`main` 직접 커밋** (트렁크 기반, PR 없음) | 가장 빠르지만 리뷰 · CI 검사를 거칠 기회가 없고, 변경 단위의 기록(PR 설명, plan 결과)이 남지 않습니다. |
| **Merge commit 허용** | 작업 브랜치의 중간 커밋이 모두 `main`에 섞여, 변경 단위로 읽기 어려워집니다. |
| **Rebase merge 허용** | 히스토리는 일직선이지만, 작업 중 커밋이 그대로 `main`에 들어가 커밋 메시지를 다듬는 부담이 생깁니다. |

## 결과

- `main` 히스토리는 "PR 1개 = 커밋 1개"가 되고, 각 커밋에서 PR 번호 `(#N)`로 설명 · 리뷰 · CI 결과를 따라갈 수 있습니다.
- 작업 브랜치 안에서는 커밋을 자유롭게 나눠도 됩니다. 병합할 때 하나로 합쳐집니다.
- 저장소 첫 커밋(`chore: 저장소 초기 구성`)만 예외로 `main`에 직접 올렸습니다. 빈 저장소에서는 PR을 만들 수 없어서이고, 직후 보호 규칙을 켰습니다.
- 개발 · 스테이징 환경이 따로 필요해지면, 브랜치를 늘리기보다 환경별 배포(예: PR마다 미리보기 배포)로 해결하는 방향을 먼저 검토합니다.
